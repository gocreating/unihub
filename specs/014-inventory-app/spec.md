# Feature Specification: Inventory App

**Feature Branch**: `014-inventory-app`

**Created**: 2026-07-10

**Status**: Draft

**Input**: User description: "Inventory app (GitHub issue #33) — Initialize a new app for users to organize their stockable items and consumables. Scenarios: CRUD for items and scenarios; prepare checklists for specific scenarios under constraints (e.g. batteries exclusive); organize/plan which item is packed inside which item for a scenario; review status for positions. Schema: item (model, serial number, amount, dimensions, size, weight, price, cost, purchase/archive time), order (store, create/arrive time), scenario, constraint."

## Clarifications

### Session 2026-07-10

- Q: The purchase-record entity was named "Order", but items can be gifts, hand-me-downs, transfers, or found — what should it be renamed to? → A: Rename "Order" to **Acquisition**; its "store" attribute becomes **source** (a store, seller, or person).
- Q: Should an acquisition record a typed method (purchase, gift, transfer, found, other), and is it required? → A: The method is a **typed** field, but it is **optional** — and linking an item to an acquisition at all is optional. A blank/absent record means the user does not recall how the item was obtained, or the item predates their use of the system.

### Session 2026-07-11

- Q: Should the catalog entity be renamed from "Item" to "SKU"? → A: **Keep "Item"**. The entity represents an individual owned/consumed thing (per-instance identity via serial number, storage location, containment), not a retail product type. "SKU" (a product-type identifier implying a product→units split) is a deliberate non-goal for v1; no product-type/variant layer is introduced.

### Session 2026-07-11 (refinement)

- Q: Should direct standalone item creation still be possible, or is creation acquisition-first only? → A: **Acquisition-first only.** Items are created within an acquisition (a standalone page where the user adds one or more items at once); there is no standalone "New Item" entry. **This supersedes the 2026-07-10 "linking is optional" decision** — every item now belongs to exactly one acquisition (`Item.acquisition` is required). An **acquisition with a blank method/source represents unknown or pre-existing origin** (the earlier "unknown origin" case).
- Q: How should inventory reference currency for price/cost given domain independence (Principle II)? → A: **Currency code string, per-field.** `price` and `cost` each carry their own currency **code string** (e.g. "USD"); the picker is populated from the finance currencies **API** (no import of finance models, no DB FK). Loose coupling preserves Principle II.
- Q: How should units on length/width/height/weight be modeled? → A: **Enum + normalize.** Each measure has a fixed unit set (length: mm/cm/m/in; weight: g/kg/lb) stored as (value, unit); a canonical base value (mm, g) is stored alongside for correct cross-unit sorting/filtering, and the value is displayed in the chosen unit.
- Q: With `item.category` removed, how should the "required" constraint work? → A: **Item set only.** A "required" constraint names specific items (≥1 must be selected); category matching (`target_category`) is dropped.
- Q: Assorted field/UX refinements (scenario nav, obtained-time consolidation, field add/remove/rename, list defaults)? → A: Scenario detail uses a **breadcrumb** (not a back button). Remove `item.purchase_time` and `acquisition.arrived_at`; the canonical obtained time is **`acquisition.obtained_at`**. Remove `item.category` and `item.storage_location`. `item.status` enum is limited to **active, deprecated** (default active). Add `item.spec` and `item.remark` (**multi-line text**); add `item.color` (string) and `item.url` (string). Rename `acquisition.notes` → **`acquisition.remark`**. Item list: **remove the active/archived toggle** (archived becomes a normal filterable attribute — the default view no longer auto-excludes archived); **default sort descending by `acquisition.obtained_at`**; **default column order**: name, spec, model, serial, size, weight, length, width, height.

### Session 2026-07-11 (UI refinement)

- Q: How should `item.status` relate to a deprecation timestamp? → A: **Status is derived from `deprecate_time`.** Setting `deprecate_time` (defaults to today 00:00:00 local) makes the item **deprecated**; clearing it returns it to **active**. `deprecate_time` **replaces `archived_at`**, and `item.status` becomes **read-only/computed** (the manual status field is removed). The "Archive" action becomes **"Deprecate"** (confirm modal collects `deprecate_time`), and a deprecated item exposes a **"Restore/Activate"** action that clears `deprecate_time`.
- Q: Add a volume attribute? → A: Add **`item.volume`** as a normalized measurement (unit set **mL, L**; canonical stored in mL), same pattern as length/weight.
- Q: Item quantity requiredness/default? → A: **`item.quantity` is required and defaults to 1.**
- Q: Currency inputs when there is no amount? → A: When `price` (or `cost`) is **0 or empty**, its currency selector is **disabled** and shows the standard **"—"** placeholder ("don't care").
- Q: Acquisition create/edit form defaults & layout? → A: `acquisition.obtained_at` **defaults to today 00:00:00** in the create form. On the acquisition form, **source / method / obtained_at share one row on wide screens and stack on narrow screens** (responsive). The Add-Item modal's fields likewise **stack on narrow screens**.
- Q: Modal & standalone-page button conventions? → A: In modals, the **Cancel button is placed left-most**; a modal **must not close on outside click while its form is dirty**. **Standalone creation/modification pages have no Cancel button** — the user navigates away via the breadcrumb. (Requested to also record this as a project-wide rule via `/speckit-constitution`.)
- Q: Can added items be edited before the acquisition is saved, and can acquisitions be edited later? → A: **Yes** — rows in the "Items in this acquisition" table are **editable** (open the item modal pre-filled, save back), and an existing **acquisition is editable on its own standalone page**.
- Q: Item/acquisition list bugs — empty column headers and inconsistent placeholders? → A: **Confirmed bugs.** Non-sortable columns (`item_count`, `total_item_cost`, `spec`, `weight`, `length`, `width`, `height`) render **blank headers** because they lack an explicit `title`; every column MUST show its localized header. Also **standardize on a single placeholder "—"** (the constitution's secondary em-dash) everywhere — no mixed short/long dashes. Add an **`acquisition.obtained_at` column** to the item list (the existing default sort ↓ by it now has a visible column), and **remove the "Add items via New Acquisition" hint** from the item list.

### Session 2026-07-11 (field trims)

- Q: Acquisition source input behaviour? → A: `source` MUST be an **auto-complete** that suggests previously-used source values (the user can still type a new value).
- Q: Keep `acquisition.method`? → A: **Remove `acquisition.method` entirely.** Unknown/pre-existing origin is now represented by a **blank source** alone. (Supersedes earlier "blank method/source" wording — method no longer exists.)
- Q: Price naming and total? → A: Rename `item.price` → **`item.sku_price`** (the per-unit / per-SKU price). A read-only **`total_price` is derived as `sku_price × quantity`**. `cost` is unchanged (the amount actually paid; still drives the acquisition's per-currency cost aggregation).
- Q: Keep `item.model` and `item.serial_number`? → A: **Remove both.** The user captures that detail in `item.spec` instead. (They also drop out of the item-list default column order.)

### Session 2026-07-11 (cost model & item cards)

- Q: "Items in this acquisition" display style? → A: Use a **card view** (not a list) on the acquisition create/edit page — each item is a card that **previews only its filled fields** (empty fields are omitted). Acceptable because an acquisition typically holds ≤ 10 items. Each card remains editable (opens the item form pre-filled) and removable.
- Q: Where should the amount actually paid live? → A: **Move cost to the Acquisition.** Remove `item.cost` and `item.cost_currency`. The **Acquisition** gains `cost` (with a currency code), `discount`, and `tax_refund`; the **net outlay is derived as `cost − discount − tax_refund`**. Items keep `sku_price` (per-unit value). This models "paying by order" and lets order-level discounts/refunds be logged once. The prior per-currency aggregation of item costs is removed (an acquisition now has a single cost currency).

### Session 2026-07-11 (request time & item minimum)

- Q: Track when an order was initiated? → A: Add **`acquisition.request_time`** — an optional timestamp for when the user initiated/requested the order (distinct from `obtained_at`, when it was received).
- Q: Minimum items per acquisition, and create-form convenience? → A: An acquisition MUST have **at least 1 item** to submit the create/edit form (0-item submit is rejected). On the **create** form, **one default (empty) item card is pre-inserted** so the user can start filling it immediately.

### Session 2026-07-11 (placeholder consistency)

- Q: The item list still shows TWO placeholder styles (short "-" in Spec/Size, em-dash "—" in the measure columns). Root cause? → A: **`PageTable`/ProTable's built-in `columnEmptyText` (default "-")** injects a short hyphen for `dataIndex` columns whose value is empty, while `key`-only columns fall through to the app's em-dash render. Fix: **`columnEmptyText={false}` on every inventory `PageTable`** so ProTable never injects its own placeholder — the app's single canonical **"—"** (secondary, `userSelect:'none'`) is the only placeholder. See FR-003.

### Session 2026-07-11 (cost factors, deprecate column, RWD)

- Q: Add a deprecate-time column to the item list? → A: Yes — the item list MUST include a **`deprecate_time` column** (alongside the obtained-date column).
- Q: Default for the acquisition `request_time` field? → A: Like `obtained_at`, `request_time` **defaults to today 00:00:00** in the create form.
- Q: Responsive layout of the acquisition form and item modal (raised repeatedly)? → A: On narrow screens the form fields MUST **stack to a single column (each field full-width)** — not half-width pairs. Note AntD `Col` breakpoints are **viewport-based**; the layout MUST stack based on the actual content width (e.g. a container query / `useContainerWidth`, or default to single-column when the content area is narrow), so a collapsed-sidebar-narrow content area also stacks.
- Q: How is the acquisition cost modelled? → A: Replace the scalar `cost`/`cost_currency`/`discount`/`tax_refund` with **1..N cost factors**. Each **CostFactor** has `value` (a **signed** decimal — negative reduces), `currency` (code string), and `type` (an informational label ∈ {accumulated, shipping, discount, tax_refund, paid_by_other, other}). **The value carries the sign; `type` does NOT affect it.** **`net_cost` is derived, read-only, and grouped by currency** — for each currency, the sum of that currency's factor values (no FX conversion).
- Q: Cost-factor minimum and the "accumulated" default? → A: An acquisition MUST have **at least one cost factor**. On create, one factor of type **`accumulated`** is auto-inserted with `value` defaulting to the **sum of the items' `total_price`** (Σ `sku_price × quantity`); the user may **override** the value or **reset** it back to the derived sum. Its currency defaults to the items' common currency (editable).

### Session 2026-07-11 (quantity int, remove type, acquisition page polish)

- Q: `item.quantity` numeric type? → A: **Integer** (whole units only).
- Q: Remove `item.type` (stockable/consumable)? → A: **Remove it entirely.** The stockable/consumable distinction is dropped from the model, item form, filters, and columns.
- Q: With `item.type` gone, what happens to the scenario checklist "shortfall" warning (which only applied to consumables)? → A: **Remove the shortfall feature entirely** — the checklist no longer computes or shows any quantity-based shortfall. `ScenarioItem.required_quantity` remains for planning, but no `shortfall` is derived.
- Q: Acquisition create/edit page title? → A: Both pages MUST title the section **"Acquisition"** (not "New Acquisition").
- Q: Acquisition breadcrumbs? → A: Create = **Acquisitions / New Acquisition** (unchanged). Edit = **Acquisitions / {acquisition.id} / Edit Acquisition** (three crumbs; the middle crumb is the acquisition id).
- Q: (bug) Editing an item's values on the acquisition page doesn't save. → A: **Critical defect — MUST be fixed.** Editing an item card (via its pre-filled modal) MUST persist the changed values: in the create flow into the pending item list, and in the edit flow to the stored item. Acceptance: change a field on an existing item card, save the modal, and the new value survives (visible on the card and after reload).

### Session 2026-07-11 (merge item + acquisition lists)

- Q: Merge the Items list and Acquisitions list into one page — how is the table structured? → A: **One merged catalog page** with an **expandable tree table**: each **acquisition is a top-level (parent) row** showing acquisition columns; expanding it reveals its **item child rows** showing item columns. The visible columns are the **union of acquisition + item columns**; a parent row populates only the acquisition columns, a child row only the item columns. Default order is still **acquisitions sorted ↓ by `obtained_at`**.
- Q: Nav entry and routing after the merge? → A: A **single nav entry labelled "Catalog"** (within the Inventory section) points to the merged list. The separate "Items" and "Acquisitions" list entries are removed; the old `/inventory/items` and `/inventory/acquisitions` list routes **redirect** to the merged page. The **create** (`/inventory/acquisitions/new`) and **edit** (`/inventory/acquisitions/:id/edit`) standalone pages are unchanged. "Scenarios" remains its own entry.
- Q: Name for the merged page? → A: **"Catalog"** — chosen over "Positions" (which would clash with US5's per-scenario "position review"/containment concept) and over "Inventory" (the nav section's own name). The merged item+acquisition list is the **Catalog**; "position" remains reserved for US5 scenario containment.
- Q: Item-row actions on the merged page? → A: **Remove the item row's "Edit" action** — items are edited only through the acquisition edit page. Item rows keep **Deprecate/Restore** and **Delete**. Acquisition (parent) rows keep **Edit** (→ standalone edit page) and **Delete** (cascades to its items), plus the page-level **New Acquisition** action.

### Session 2026-07-11 (catalog & cost UI, iteration 5)

- Q: How should the auto-derived "accumulated" cost factor be scoped (the mockup shows one "Items" row per currency, but "at most 1 accumulated" was also requested)? → A: **One accumulated factor per distinct item currency**, system-managed: for each currency present among the items' `sku_price`, an `accumulated` factor is auto-derived (`value` = Σ `sku_price × quantity` for that currency). These rows are **labelled "Items", non-removable, individually resettable**, and users **cannot create** `accumulated` factors manually. "At most 1 accumulated" means **at most one accumulated factor per currency** (uniqueness on `(acquisition, type='accumulated', currency)`). Users may still **override** an accumulated row's value (reset restores the derived sum).
- Q: How is the cost-factor `type` stored/validated now that it mixes built-in enums with user text? → A: **Free-form non-empty string.** The six built-ins (accumulated, shipping, discount, tax_refund, paid_by_other, other) become **autocomplete suggestions**, not a closed enum — the DB choices constraint is dropped. **`accumulated` is system-reserved** (not user-selectable). i18n labels apply to known suggestions; unknown values render verbatim.
- Q: Should the user-defined order of cost factors be persisted (the mockup shows drag handles)? → A: **Yes.** CostFactor gains an explicit **`display_order`** integer; factors render in saved order with the **accumulated ("Items") rows pinned to the top** (not draggable). Manual factors are **drag-reorderable**, and the order is saved with the acquisition.
- Q: Cost panel layout and placement? → A: Rename the section **"Cost Factors" → "Cost"** and move it to the **end of the form, below the Items panel**. Its header carries the **[Add]** action. The derived per-currency **net cost moves to the panel footer, labelled "Total"** (one line per currency). Each factor row is: `[drag]` (manual only) · `type` · **`value`+`currency` composed as one control with the value right-aligned** · trailing action (**[reset]** for accumulated rows, **[remove]** for manual rows). Rows MUST **fill the container width** and, when stacked on a narrow content area, MUST have a **vertical gap** between rows.
- Q: Catalog page refinements? → A: (a) Use an **arrow (▸/▾) expansion icon**, not plus/minus. (b) **Split the "Name / Source" column into two separate columns** — a **Source** column (acquisition rows) and a **Name** column (item rows). (c) **Size the Actions column to fit its content** (buttons must not clip/overflow). (d) **Remove the "Acquisition" badge** on parent rows.
- Q: Other create-acquisition refinements? → A: **`obtained_at` also defaults to today 00:00:00** on create (like `request_time`). Rename the items panel heading **"Items in this acquisition" → "Items"**. **Item cards MUST display their filled attribute values** (e.g. quantity, sku_price, size, spec, color, dimensions, weight, volume, url) — every non-empty field is shown on the card, not just a subset.

### Session 2026-07-11 (catalog & cost UI polish, iteration 6)

- Q: Which column should the Catalog add ("add requested column")? → A: Add the acquisition **`request_time` ("Requested")** column to the Catalog (acquisition rows populate it; item rows blank).
- Q: All columns must be filterable/sortable, but Catalog is a tree — how should item-level filter/sort behave? → A: **Flatten on item filter/sort.** Acquisition columns (Source, Requested, Obtained, Net cost, Items count) filter/sort the parent tree as today. Applying a **filter or sort on an item-level column** (Name, Spec, Size, Weight, Status, Quantity, SKU price, URL, dimensions) switches the Catalog to a **flat, ungrouped item list** filtered/sorted by that column; clearing item filters/sorts restores the acquisition tree. Every column MUST expose filter + sort controls in the toolbar.
- Q: Catalog tree presentation? → A: (a) Use a **caret icon** (`CaretRight`/`CaretDown`) for the expand toggle — supersedes the ▸/▾ arrow from iteration 5. (b) The tree is **expanded by default** (all acquisition rows show their items on load). (c) **Column/cell widths MUST dynamically fit their content** (measured per column across rows) — no clipped or over-narrow cells (recurring bug).
- Q: Catalog columns added this iteration? → A: Add **Quantity, SKU price (+currency), URL (clickable), and dimensions (Length/Width/Height)** as item columns, plus the **Requested** acquisition column above. All are toolbar-filterable/sortable per the flatten rule.
- Q: Acquisition create/edit refinements? → A: (a) The breadcrumb's first crumb changes **"Acquisitions" → "Catalog"** (links to `/inventory/catalog`). (b) When an item has a **`url`**, the item **card header is a link** that opens the URL in a **new tab** (`target="_blank"`, `rel="noopener"`).
- Q: Cost panel polish? → A: (a) The accumulated **[reset]** action is an **icon-only button** (no text — it was overflowing/breaking the row layout). (b) Cost-factor rows MUST **stack to a single column on a narrow content area** (same content-width behaviour as the Acquisition panel fields — currently they don't stack). (c) The accumulated rows' **displayed label is "Items"** (not "Accumulated").
- Q: Regression coverage for these repeatedly-reported UI issues? → A: Add **Playwright e2e specs** under `apps/unihub/frontend/e2e/` asserting each fixed behaviour (caret icon, default-expanded tree, dynamic column widths, Requested column present, flatten-on-item-filter, breadcrumb "Catalog", item-card URL opens a new tab, reset is an icon-only button, cost rows stack when narrow, accumulated label reads "Items"). These run against the live stack (Docker backend + `pnpm dev`), like the existing e2e specs.

### Session 2026-07-11 (catalog fit/stability, cost/modal fixes, CNY, iteration 7)

- Q: Catalog cell widths (reported not fixed for Name/Spec/Actions)? → A: **Column widths MUST fit content AND account for tree-view expansion** — the measured width for the first (tree) column MUST include the **caret column + per-level indentation**, and the **Actions column MUST be measured too** (currently unbounded). No column may clip or over-narrow, expanded or collapsed.
- Q: SKU price formatting? → A: SKU price MUST **drop trailing zeros** (e.g. `10.0000 → 10`, `59.9000 → 59.9`) wherever it is displayed (Catalog + item cards).
- Q: Catalog pagination (it disappeared)? → A: **Restore pagination** — the Catalog MUST paginate (client-side over the single fetched data set), not render every row with only a count.
- Q: The "Items" (item_count) column? → A: **Remove it** — the item-count column is unnecessary.
- Q: Caret placement? → A: The expand **caret MUST occupy its own dedicated (narrow) column**, not be merged into the Source/first data column.
- Q: Data joining and the flash/jitter on navigation? → A: Acquisitions and their items MUST be **joined on the backend and fetched once** by the frontend (already nested); the Catalog MUST **not flash/jitter on navigation** — cache the data (no refetch-on-mount flash) and compute column widths + default-expansion **without a post-render layout shift**.
- Q: Cost-panel `type` display? → A: The cost-factor `type` MUST **display a human-readable localized label**, not the raw key. Built-ins **store a stable key** (accumulated/shipping/discount/tax_refund/paid_by_other/other) and render their **localized label**; free-form text is stored and shown **verbatim**.
- Q: Cost-panel field layout? → A: The Cost-panel fields MUST **follow the form-grid constitution** (Principle VI): grid `Row`/`Col`, each field stretches to fill and together fill the row, **stack to one column on a narrow content area**, and **number inputs right-align**.
- Q: Add-Item modal field order? → A: Fields MUST be ordered: **Name, quantity, SKU price, spec, URL, remark, color, size, weight, length, width, height, volume**.
- Q: Add-Item modal layout compliance? → A: The modal MUST **follow the form-grid constitution** (grid, fields fill rows, stack on narrow content width, right-aligned number inputs).
- Q: Item-card body content? → A: Item cards MUST render their **available optional attributes as badges** (Ant Design `<Tag>`) in the card body (only non-empty attributes shown).
- Q: Currency for the legacy import (RMB vs CNY)? → A: unihub uses **CNY**, not RMB. The importer MUST **normalize RMB → CNY**; the previously-imported 2026 acquisitions MUST be **deleted and re-imported** as CNY.

### Session 2026-07-11 (data_io integration, iteration 8)

- Q: Is the inventory app integrated with the existing data-migration feature (`data_io` CSV import/export/change-preview registry)? → A: **No — it was a gap.** Inventory registered **zero** `TableDescriptor`s (finance registers all its tables in `AppConfig.ready()`). It MUST be integrated: `inventory/apps.py` gains a `ready()` that registers its tables via `data_io.registry.register(TableDescriptor(...))`.
- Q: Which inventory tables to register? → A: Register **five** — `inventory.acquisition`, `inventory.item` (FK→acquisition), `inventory.costfactor` (FK→acquisition), `inventory.scenario`, `inventory.scenarioitem` (FK→scenario/item + self-FK container) — with `import_order` parents-before-children and `fk_content_type_label` overrides. **Constraint is deferred** because the registry has **no M2M support** (`Constraint.items` is a M2M) — revisit when the registry supports M2M / a join-table export. All inventory tables use **`has_user_attributes=False`** (concrete columns; no `AttributeValue`s).
- Q: Fate of the one-off legacy importer (`import_legacy_csv`)? → A: **Keep both.** `import_legacy_csv` stays for the external 財產們 spreadsheet (grouping/備註-parsing/RMB→CNY — a one-time migration); `data_io` provides standard per-table CSV backup/round-trip. They serve different purposes.
- Q: Governance so this gap can't recur? → A: **Amend the constitution** (Principle I / data-integrity governance): **every schema change MUST keep the domain consistent with the `data_io` feature** — a new concrete model MUST register a `TableDescriptor` (with FK overrides + import order), and adding/removing/renaming a field MUST update that descriptor, in the **same change**. (Constitution amendment tracked as part of this iteration.)

### Session 2026-07-11 (catalog width/pagination/URL — reuse canonical patterns, iteration 9)

- Q: Catalog column widths still don't fit content for Name/Spec (and look fixed) — why? → A: **Root cause identified**: the canonical `dataWidths` measurement (`measureTextWidth` per column → `widthForHeader`) was run **only over the top-level acquisition rows**; the item **child rows are nested (`children`) and were never measured**, so every item column fell back to its fixed `min`. **Fix**: reuse the exact same finance/PageTable width pattern but measure the **full displayed set (acquisition rows + their item rows)** so Name, Spec, and every column size to their real content.
- Q: Pagination — what pattern? → A: **Follow the existing table pagination pattern verbatim** (as finance/other pages): `pagination={false}` + `footer={() => <EntityOffsetFooter {...table.paginationProps(total)} />}` with **server-side offset pagination** (identical layout, per-page selector, total metric, page navigation, UI/UX). No ad-hoc AntD `pagination` object.
- Q: With server-side pagination, how do all columns stay filterable/sortable? → A: **The backend supports filter + sort + pagination across all columns.** Tree mode paginates **acquisitions** server-side (`AcquisitionViewSet`) with nested items; when a filter/sort targets an **item column**, the Catalog switches to a **server-paginated flat item list** (`ItemViewSet`, whose `filterable_fields`/`ordering_fields` are **extended to cover every catalog item column** — name, spec, size, weight, length, width, height, quantity, sku_price, status, plus `source`/`obtained` via `acquisition__…`). The derived multi-currency `net_cost` is display-only (not sortable). No client-side fetch-all.
- Q: Item URL presentation? → A: **Remove the URL column.** Instead, the item **Name cell becomes a link** (`target="_blank"`, `rel="noopener"`) to the item's `url` when present; plain text when absent.

### Session 2026-07-11 (catalog defaults, nulls sort, form-constitution enforcement, iteration 10)

- Q: Catalog default column order? → A: **Net cost, Name, SKU price, Source, Requested, Obtained** (then the remaining item columns, then Actions). Because column config persists in `localStorage`, the table's persistence key MUST be **versioned/bumped** so the new defaults take effect for existing users.
- Q: Catalog default sort? → A: **Obtained descending, nulls first** — applied as the explicit backend default (`-obtained_at__nullsfirst` on `AcquisitionViewSet`; `-acquisition__obtained_at__nullsfirst` on `ItemViewSet`) AND seeded into the toolbar's sort state so the UI reflects it.
- Q: Why doesn't nulls-first/last take effect (critical bug)? → A: The plumbing (SortPanel → `__nullsfirst`/`__nullslast` suffix → `NullsOrderingFilter`) exists but the Catalog had **no explicit nulls default and no test proving the path**; the tree-mode prefix-strip (`acquisition__…`) additionally rewrites the ordering token. **Fix + lock**: explicit nulls defaults (above) and **backend + e2e tests** asserting that `?ordering=-obtained_at__nullsfirst` / `__nullslast` reorder null `obtained_at` rows correctly through the API, and that the strip preserves the nulls suffix.
- Q: Requested/Obtained display? → A: **Date only** (`YYYY-MM-DD`), not full datetime, keeping the relative suffix (`(X days ago)`) — an explicit spec override of the constitution's default `YYYY-MM-DD HH:mm` format for these two Catalog columns.
- Q: Button labels? → A: Catalog page action **"New Acquisition" → "New"**; acquisition create submit **"Create Acquisition" → "Create"**; Items panel **"Add Item" → "Add"**; Cost panel **"Add Factor" → "Add"** (both locales).
- Q: Numeric column alignment? → A: **Net cost and SKU price cells right-align** their content (AntD column `align: 'right'`).
- Q: Why does the Add-Item modal violate the form constitution (critical bug)? → A: Three distinct root causes: (a) **stacking** — `useContainerWidth` attaches its `ResizeObserver` in a mount-time effect, but AntD `Modal` **lazy-mounts its children on first open**, so `ref.current` is null when the effect runs and the observer never attaches → `isNarrow` never becomes true inside modals. **Fix: a callback ref** that attaches/detaches the observer whenever the node actually mounts. (b) **numeric right-align** — the global rule lives in `index.css`, which loads **before** AntD's runtime cssinjs styles; equal specificity + later injection means AntD's `text-align:left` wins. **Fix: a higher-specificity selector** (e.g. `.ant-input-number .ant-input-number-input`). (c) **Cancel placement** — AntD's default modal footer renders the whole button group right-aligned; the constitution requires **Cancel on the left-hand side** of the footer with the primary on the right. **Fix: custom `space-between` footers** (Cancel flushed left, primary right) on ALL inventory modals (Add-Item, Deprecate, Constraint).

## User Scenarios & Testing *(mandatory)*

The Inventory domain is a new section of the unihub dashboard where a user catalogs everything they own or consume, records how those things were acquired, and plans which items to take and how to pack them for real-world situations (a trip, a shoot, an event). Each user story below is an independently shippable slice.

### User Story 1 - Catalog and manage items (Priority: P1)

The user maintains a personal catalog of physical things they own. Items are added through an acquisition (see User Story 2) rather than a standalone form. The user records each item's core attributes — quantity (integer, default 1), spec, remark, sku_price (with a currency), url — plus **on-demand parameter rows** (key · value · optional unit, backed by the shared attribute infrastructure; system keys like color/size/weight/length/width/height/volume are pre-seeded, and the user can define new keys with a chosen type), edits it as details change, **deprecates** it when it leaves active use (setting `deprecate_time`, which makes its derived status "deprecated") or **restores** it to active, and browses/searches/filters the full catalog in a tabular view.

**Why this priority**: The item catalog is the foundation of the entire domain — acquisitions reference items, scenarios select items, and packing plans arrange items. Nothing else in the feature has meaning without it. Shipping only this story already delivers value: a searchable record of everything the user owns.

**Independent Test**: Can be fully tested by creating several items with varied attributes, editing one, deprecating one (and restoring it), and confirming they appear (with the derived status distinguishable/filterable) in the catalog table with working search, sort, and filter — no other story required.

**Acceptance Scenarios**:

1. **Given** an acquisition being created (User Story 2), **When** the user adds an item with a name, an integer quantity, any subset of core attributes (spec, remark, sku_price with a currency, url), and zero or more parameter rows (a pre-seeded key like weight with a unit, or a newly defined key with a chosen type), **Then** the item and its parameters are saved under that acquisition and appear in the catalog table.
2. **Given** an existing item, **When** the user edits one or more of its attributes, **Then** the updated values are persisted and reflected in the table.
3. **Given** an existing item, **When** the user deprecates it (confirming a `deprecate_time` that defaults to today 00:00:00), **Then** its derived status reads "deprecated" and it is locatable via the `deprecate_time` filter; a subsequent **Restore** action clears `deprecate_time` and the status returns to "active".
4. **Given** a catalog with many items, **When** the user opens the merged Catalog page, **Then** acquisitions are shown as parent rows sorted descending by their obtained date; single-item acquisitions render as one merged collapsed row and multi-item acquisitions expand to item child rows — showing by default the derived **Item** (name-link + spec + ×quantity tertiary), **SKU price**, and **Parameters** (one badge per parameter row) columns — with name, url, spec, status, deprecate_time, and **every parameter definition (system and user-defined)** available as individually toggleable hidden columns; every column shows its header; and the user can search, sort, or filter (including by deprecated status or by any parameter key) as needed.
5. **Given** an item with a quantity on hand, **When** the user updates its quantity, **Then** the new (integer) quantity is persisted and displayed.
6. **Given** the item entry within an acquisition, **When** the user submits an item without a required identifying field (name), **Then** the system rejects it with a clear validation message and no item is created.

---

### User Story 2 - Acquire items (acquisition-first creation) (Priority: P1)

Adding items to the catalog is done through an acquisition on a dedicated, standalone page. The user opens "New Acquisition", records how the batch was obtained — source (a store/seller, or a person for gifts; entered via auto-complete over previously-used values), the date obtained, and an optional remark — then adds **one or more items** in the same flow, each with its own attributes. This is the only way items enter the catalog: every item belongs to exactly one acquisition. An acquisition with a **blank source represents unknown or pre-existing origin** (e.g. items the user already owned before using the system).

**Why this priority**: This is now the entry point for the entire catalog (creation happens here), so it is co-critical with browsing the catalog. Without it there are no items.

**Independent Test**: Create an acquisition with cost factors (an accumulated factor plus a negative discount factor) adding two items at once (as cards) and a "blank" acquisition adding one pre-existing item; confirm all three items appear in the catalog, each links back to its acquisition, and each acquisition shows its item cards and its derived per-currency net_cost.

**Acceptance Scenarios**:

1. **Given** the standalone New Acquisition page, **When** the user fills the acquisition fields and adds two or more items each with a name and attributes, **Then** the acquisition and all its items are saved together and the items appear in the catalog.
2. **Given** an acquisition with items, **When** the user views the acquisition, **Then** it displays the source, request and obtained dates, remark, the item cards, and the cost factors with the derived per-currency net_cost.
3. **Given** an item, **When** the user views it, **Then** its originating acquisition (source and obtained date) is shown.
4. **Given** an acquisition with a blank source, **When** the user views its items, **Then** their origin reads as unknown/pre-existing without error.
5. **Given** an acquisition, **When** the user adds or removes an item, **Then** the acquisition's item cards update accordingly, and the derived value of the per-currency **`accumulated` factor(s)** (one per item currency, if not manually overridden) reflects the new item-total sum.
6. **Given** an acquisition, **When** the user deletes it, **Then** its items are also removed from the catalog with a confirmation warning (items cannot exist without an acquisition), OR the user is required to reassign them first.

---

### User Story 3 - Define scenarios and assemble their items (Priority: P2)

The user defines a scenario — a named situation such as "Weekend camping" or "Studio photo shoot" — with a **name and an optional description** (shown in a standalone panel on the detail page), then assembles its item set in the **Organize panel**: an **Add button opens a search modal** (highlighted matches, members disabled) to bring items into the scenario's **unorganized pane**, and a **Splitter** separates that flat list from the drag-arranged packing tree (see User Story 5 for containment semantics). *(The preparation checklist — prepared state, progress tracking — is **deferred** as of iteration 14, along with constraints.)*

**Why this priority**: This is the primary planning payoff of the domain and the first story that turns a static catalog into an actionable tool. It depends on User Story 1 but not on acquisitions.

**Independent Test**: Create a scenario with a name and description; on its detail page, fuzzy-search the backlog for a known item fragment, add two items, and confirm they appear in the Organize tree and persist across a reload; confirm the scenario list shows exactly Name, Description, and Actions columns.

**Acceptance Scenarios**:

1. **Given** the scenario list page, **When** the user creates a scenario with a name and optional description, **Then** it is saved and the list shows it with exactly three columns: Name, Description, Actions.
2. **Given** the Organize panel's Add modal, **When** the user types a fragment, **Then** matching catalog items (case-insensitive substring on name/spec) are listed with the match highlighted and item names hyperlinked to their `url`; items already in the scenario appear disabled.
3. **Given** enabled search results, **When** the user adds an item, **Then** it joins the scenario in the UNORGANIZED pane and its search-result row becomes disabled.
4. **Given** an unorganized item, **When** the user removes it from the scenario, **Then** it leaves the pane and becomes addable (enabled) in the search modal again; tree items offer no remove — dragging them to the unorganized pane is the only way out of the tree.

### User Story 4 - Enforce constraints on scenarios — REMOVED (iteration 14)

**Removed to reduce system complexity.** All constraint functionality (mutual exclusivity, required-item rules, weight limits — model, API, and UI) is deleted in iteration 14; the `Constraint` table is dropped by migration (it was never registered with `data_io`, so no descriptor changes). The concept may return as a future feature with its own spec.

### User Story 5 - Plan item packing and review positions (Priority: P3)

The user organizes items into a physical containment plan for a scenario via the **Organize panel's drag-and-drop tree** — dragging an unorganized item into the tree organizes it (onto a node nests; elsewhere appends top-level), dragging an item onto another item nests it inside that container (a container is itself an item: camera goes in the padded case, case goes in the backpack), dragging among siblings sets their persisted order, and dragging a tree item back to the unorganized pane un-organizes it. Reviewing the tree shows, for any item, which container it is packed inside (or that it is top-level) and everything nested within any container.

**Why this priority**: Packing/containment and position review is the most advanced planning capability and depends on both the catalog and scenarios. It is the last slice because it delivers refinement rather than core function.

**Independent Test**: Can be tested by dragging one item onto another in the Organize tree, confirming the nesting and sibling order survive a reload, and confirming an item cannot be placed inside itself or form a containment cycle.

**Acceptance Scenarios**:

1. **Given** items in a scenario, **When** the user drags an item onto a container item in the Organize tree, **Then** the containment relationship is saved and the child appears nested under the container.
2. **Given** a container with nested items, **When** the user expands it in the tree, **Then** all directly-contained items are listed and multi-level nesting is navigable.
3. **Given** siblings under the same parent, **When** the user drags one to a new position, **Then** the sibling order persists (survives reload).
4. **Given** a containment action that would place an item inside itself or create a cycle (A in B, B in A), **When** the user attempts it, **Then** the system rejects the action with a clear message.
5. **Given** items and containers, **When** the user reviews the Organize tree, **Then** each item's current position (container or top-level) is visible in one view.

### Edge Cases

- **Deprecated items in plans**: What happens when an item that is part of an active scenario is deprecated? The item remains referenced with a clear deprecated indicator; it is not silently removed from existing plans.
- **Deleting a referenced item**: How does the system handle deleting an item that is linked to acquisitions, scenarios, or used as/inside a container? Deletion is blocked or the references are cleanly detached with a warning, rather than leaving dangling references.
- **Container removed or sent back while holding items**: When a container line is removed from the scenario (only possible while unorganized) or **sent back to the unorganized pane**, its directly-nested items are **re-parented to the organized tree's top level** (never deleted from the scenario, never unorganized implicitly).
- **Empty scenario**: Both Splitter panes show empty states directing the user to the Organize panel's Add button; the search modal works normally.
- **Duplicate parameter key**: An item MUST NOT hold two values for the same parameter key — the editor prevents adding a key already present on the item (enforced by the `(definition, entity)` uniqueness).
- **Deleting a user-defined parameter definition with values**: MUST show a confirmation stating the count of affected items; on confirm, its AttributeValues are removed (Principle I). System definitions cannot be deleted or renamed.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow the user to create (via an acquisition — FR-006), view, edit, and deprecate items, where each item records at minimum a name and an **integer** quantity (required, default 1), a **stored `deprecated` boolean** (iteration 36 — `deprecate_time` records WHEN, optional/nullable, for the unknown-time case; `status` derives from the flag), plus optional **core attributes**: **`alias_name`** (the user's own familiar name — iteration 18, see FR-030), spec (multi-line), remark (multi-line), sku_price (with a currency), and url — and **zero or more parameters** (FR-026). A read-only **`total_price` is derived as `sku_price × quantity`**. Every item belongs to exactly one acquisition. (No `type`, `model`, `serial_number`, per-item `cost`, or concrete color/size/measurement columns — those are parameters as of iteration 14.)
- **FR-002**: An item is **deprecated** by setting `deprecate_time` (the "Deprecate" action; its confirm dialog collects the timestamp, defaulting to **today 00:00:00** local). Setting `deprecate_time` marks the item deprecated; a **"Restore/Activate"** action clears `deprecate_time` and returns the item to active. `deprecate_time` is a filterable attribute; the default view does not auto-exclude deprecated items.
- **FR-002a**: `item.status` is **derived, read-only**: **deprecated** when `deprecate_time` is set, otherwise **active**. There is no separately-editable status field, and no separate `archived_at` (deprecate_time is the single lifecycle timestamp). The status column MUST reflect the derived value.
- **FR-002b**: **Dimension-typed parameters** MUST carry a unit from their definition's fixed **unit family** (length: mm/cm/m/in, canonical mm; weight: g/kg/lb, canonical g; volume: mL/L, canonical mL; **temperature: °C/°F, canonical °C (affine); time: s/min/h, canonical s; battery: mAh/Ah, canonical mAh** — iteration 26) and MUST store the normalized canonical value alongside the entered value+unit so that sorting and filtering compare correctly across mixed units. **A dimension OR number-typed value MAY be a RANGE `min-max`/`min~max`** (iterations 26→28): the canonical MIN is the sort/filter key (`value_number`) and the canonical MAX persists in **`value_number_max`** (null for single values); ranges display as **`min ~ max unit`** (tilde — iteration 28; unitless for the number type). The editor's dimension and number value inputs use an **explicit mode toggle** (iteration 30): **exact** — one numeric field — or **range** — two numeric fields joined by `~` (both required; min ≤ max validated inline); the mode initializes from the stored value and the emitted text stays canonical (`74` / `74~164`). The seeded system definitions weight/length/width/height use the corresponding families (weight → weight; length/width/height → length; volume → volume); user-defined dimension parameters choose their family at definition time (FR-027).
- **FR-002c**: Monetary fields carry a currency stored as a currency **code string** — the item's `sku_price` and each acquisition **cost factor** (see FR-006). The currency picker is populated from the finance domain's currencies **via its API** (no import of finance models and no cross-domain database foreign key — Principle II). When the associated amount is 0 or empty, its currency selector MUST be **disabled** and show the standard "-" placeholder (short dimmed hyphen, constitution v1.20.0).
- **FR-003**: System MUST present a **single merged "Catalog" page** (Items and Acquisitions lists combined) as an **expandable tree table** on `PageTable`: each **acquisition is a parent row** (populating acquisition columns) that expands to reveal its **item child rows** (populating item columns). Expansion MUST use a **caret icon** (`CaretRight`/`CaretDown`) that occupies its **own dedicated (narrow) column** (not merged into the Source/first data column) which is a **real toggleable column — listed in the Columns dropdown (label "Toggle") and PINNED (sticky-left) in the default column state** (iteration 16); MULTI-item acquisitions MUST be **expanded by default**; a SINGLE-item acquisition renders **collapsed by default as ONE merged row** combining both entities (FR-003b). Columns are the **union** of acquisition columns and item columns, with **`Source` and `Name` as two separate columns** (acquisition rows populate `Source`; item rows populate `Name`) — acquisition columns: source, `request_time` ("Requested"), `obtained_at` ("Obtained"), net_cost, plus the **derived "Acquisition" column**; item columns: name, **alias (`alias_name`, hidden by default — FR-030)**, url, spec, `quantity`, `sku_price` (+currency, **trailing zeros dropped**), status, `deprecate_time`, **one dynamic column per parameter definition (system + user-defined, FR-028)**, plus the **derived "Item" and "Parameters" columns** (derived columns per **FR-003a**); a parent row leaves item columns empty and vice-versa (standard "-"). There is **no "Acquisition" badge** on parent rows and **no item-count ("Items") column**. A **`url` column exists but is hidden by default** — its earlier total removal was a defect: **every catalog column MUST appear in the column-visibility dropdown** regardless of default visibility. The **derived "Item" column's primary row is a link** (`target="_blank"`, `rel="noopener"`) to the item's `url` when present, plain text otherwise; the **`Name` column renders plain text — NO hyperlink** (iteration 17: the Item column carries the sole link). **Column widths MUST dynamically fit their content using the canonical `dataWidths` pattern** (`measureTextWidth` per column → `widthForHeader`, same as the finance pages) — measured over the **full displayed row set INCLUDING the item child rows** (the earlier defect measured only parent rows, so item columns like Name/Spec fell back to a fixed `min`); the **Actions column is measured** too; **no arbitrary per-column minimum floors** (width = max(content, header) + padding — a second defect inflated e.g. Net Cost with a 140px floor); no column clips or over-narrows. **Measure-what-you-render (iteration 17)**: a cell that renders its content ellipsised at a fixed cap (the `url` column caps at 320px) MUST have its measured width **capped to match the render** — never sized to unrendered raw text — and the ellipsised link carries a **truncation-gated Tooltip** with the full URL (constitution v1.20.0). **Every column MUST be filterable and sortable — served by the backend** (server-side filter + sort + pagination). The **derived `net_cost` (multi-currency aggregate), derived `status`, and the three derived presentation columns ("Item", "Parameters", "Acquisition" — FR-003a) are display-only** (not filter/sortable — a documented exception, as with computed columns elsewhere). The column-config persistence key is **versioned (v5 as of iteration 15)** so new defaults apply over previously-saved state. **Requested and Obtained follow the constitution's two-row datetime default** (absolute `YYYY-MM-DD HH:mm` primary row, relative time as a muted secondary row — the earlier date-only single-line override is rescinded). **Net cost and SKU price cells right-align.** The page-level action button is labelled **"New"** (not "New Acquisition"). **Item rows have no "Edit" and no "Delete" action** (items are edited on the acquisition edit page and hard-deleted there or via acquisition deletion); item rows keep **only Deprecate/Restore**; acquisition rows keep **Edit only** (iteration 19): the Edit action is a **real hyperlink** (`href` to the edit page, button appearance) so it opens in a new tab without losing the catalog context, and **Delete is REMOVED from the catalog** — it lives in the acquisition edit page's panel kebab (FR-007, constitution v1.21.0). **In FLAT mode every item row's Actions cell additionally carries its parent acquisition's Edit hyperlink** (iteration 21 — flat mode has no acquisition rows, so the link must ride the item rows; tree-mode child rows don't duplicate it).
- **FR-003a**: The Catalog MUST provide three **read-only derived presentation columns** (display-only — no filter/sort; localized headers; each renders the standard "-" placeholder on rows of the other level, except "Acquisition" in flat mode):
  - **"Item"** (item + merged rows): **primary row = the alias-preferred display name** (`alias_name` when set, else `name`; when aliased, a tooltip shows the original `name` — FR-030), rendered as a hyperlink to the item's `url` (`target="_blank"`, `rel="noopener"`) when present, plain text otherwise; **secondary row = `spec`** (muted secondary text, single line, ellipsised — Tooltip ONLY when actually truncated, constitution v1.20.0), rendered only when non-empty; **tertiary row = `×{quantity}`** (muted), rendered **only when quantity > 1**. **Width (iteration 27)**: the Item column's measured width derives from the **primary name line only** (alias-preferred name; the ×N tertiary counts, the spec line does NOT) — the spec secondary **truncates at the COLUMN width** with its gated tooltip; a long spec must neither widen the column nor truncate against the row's own name width.   - **"Parameters"** (item rows): **one Ant Design `<Tag>` badge per parameter row** on the item. - **FR-003b**: **Merged single-item rows.** An acquisition with EXACTLY ONE item renders, when collapsed (the default), as a **single combined row**: the Acquisition derived column carries the acquisition summary while the item-side columns (Item, SKU price, Parameters, status, and any toggled item columns) carry the item's values; the row's Actions cell offers **both entities' actions** (the acquisition's Edit hyperlink; Deprecate/Restore for the item — no Delete on the catalog as of iteration 19). The caret **expands the merged row into the classic two rows** (acquisition parent + item child, each with its own actions) and collapses back. Width measurement includes merged rows; sorting/filtering semantics are unchanged (the merged row IS the acquisition row).
- **FR-004**: System MUST track an **integer** quantity for items (required, default 1) and allow the user to update it.
- **FR-005**: System MUST validate item input and reject creation/update that omits required information (name, quantity) or contains invalid values (e.g. negative quantity, a non-numeric value for a numeric/dimension parameter, a unit outside the definition's family, a select value outside the definition's options), returning clear messages.

On the acquisition form, source / request_time / obtained_at MUST share one row on wide screens and **stack to a single full-width column on narrow screens** — the stacking MUST respond to the actual content width (not only the raw viewport). Creating items outside of an acquisition MUST NOT be offered. The items section MUST be titled **"Items"** and **render as a card view** (one card per item). ### Key Entities *(include if feature involves data)*

- **Item**: A physical thing the user owns. Concrete attributes: name, **`alias_name`** (optional user-familiar name, alias-preferred in displays — FR-030), quantity (**integer**, required, default 1), spec (multi-line), remark (multi-line), sku_price (per-unit, with currency code), url, and `deprecate_time`; everything else lives in **Parameters** (below). Derived: **`total_price` = `sku_price × quantity`** (read-only). **`status` is derived** (deprecated when `deprecate_time` is set, else active) — not a stored, editable field. Belongs to exactly one **Acquisition**. May act as a container holding other items. Central entity referenced by scenarios and containment relationships. (No `type`, `model`, `serial_number`, `cost`, `category`, `storage_location`, `purchase_time`, separate `archived_at`/`status`/`price`, or — as of iteration 14 — concrete color/size/weight/length/width/height/volume columns.)
- **Parameter** (shared `AttributeDefinition` + `AttributeValue`, core): A key-value pair (optional unit) on an Item. The **definition** carries the key name, **type** (string, numeric, **dimension** — new core data type — or select), unit family for dimension types, options for select types, and `is_system` (the seven seeded keys are protected). The **value** stores the entered value (+unit for dimension) and a **canonical numeric** (dimension: family base unit; numeric: the number) for correct cross-unit sort/filter. Uniqueness: one value per (definition, item).
- **Acquisition** (formerly referred to as "Order"): A record of how a batch of one or more items was obtained and paid for, and the sole creation path for items. Attributes: source (a store, seller, or person; entered via auto-complete), `request_time` (when the order was initiated), `obtained_at` (when received), remark. Owns **at least one** item (composition — deleting it removes its items) and **1..N cost factors**. Derived: **`net_cost`** = per-currency sum of its cost-factor values (read-only). A blank source signifies unknown/pre-existing origin. (No `method`, `arrived_at`, arrival status, per-item cost, or scalar `cost`/`discount`/`tax_refund` — those are now cost factors.)
- **CostFactor**: A signed line of an acquisition's payment. Attributes: `value` (signed decimal — negative reduces net cost), `currency` (code string, finance-API picker), `type` (**free-form non-empty string**; built-ins accumulated/shipping/discount/tax_refund/paid_by_other/other are suggestions, not a closed enum), `display_order` (integer, user-defined ordering). The **value carries the sign**; the type does not. Belongs to exactly one Acquisition (composition). The **`accumulated` type is system-managed and unique per currency**: for each distinct item currency the system derives one `accumulated` factor whose value = Σ (`sku_price × quantity`) for that currency; these are non-removable, not user-creatable, and user-overridable/resettable. All other factors are user-added, removable, and drag-reorderable (accumulated pinned to top).
- **Scenario**: A named situation for which the user assembles a set of items (e.g. a trip or event). Attributes: **name** (required), **description** (optional multi-line; renamed from `notes`). Owns its item memberships and their containment tree. *(Checklist/progress and constraints removed in iteration 14 — see US4.)*
- **ScenarioItem / Containment relationship**: A scenario's membership record for an item — links scenario + item, an optional **container** (self-referential: the ScenarioItem it is packed inside; acyclic, cycle-checked server-side), **`display_order`** (persisted sibling order in the Organize tree), and **`organized`** (boolean, default false — iteration 16: false = the unorganized flat pane, true = the packing tree). *(No `prepared` or `required_quantity` as of iteration 14.)*

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can add a new item to the catalog with its core attributes in under 1 minute.
- **SC-002**: A user can locate any specific item in a catalog of at least 500 items in under 15 seconds using search, sort, or filter.
- **SC-003**: A user can go from creating a new scenario to a populated, organized item tree (≥5 items added via the search modal and dragged from the unorganized pane into the tree) in under 3 minutes.
- **SC-004**: *(retired in iteration 14 — constraints removed; see US4)*
- **SC-005**: For any packed item, a user can determine its current position (the container it is inside, or top-level) in a single view without manual cross-referencing.
- **SC-006**: The system prevents 100% of invalid containment attempts (self-containment and cycles) with a clear message.
- **SC-007**: No acquisition or scenario operation ever deletes or corrupts an item record — item count is preserved across all acquisition/scenario edits and deletions in testing.

- **SC-009**: A user can add a brand-new kind of parameter (define key + type, set a value) to an item without any code or schema change, and immediately filter/sort/column the catalog by it.

## Assumptions

- **Single-user, personal scope**: Inventory data belongs to the authenticated user, mirroring the personal-hub model of existing unihub domains; no multi-user sharing, lending, or team collaboration is in scope for this feature.
- **Quantity is manual**: Automatic consumption/depletion driven by usage events is out of scope; quantity changes are manual. (The earlier stockable/consumable classification was removed with `item.type`.)
- **Item is an individual possession, not a product type (SKU)**: The catalog entity is called **Item** and represents a specific owned thing. A retail-style product-type/variant layer ("SKU" with multiple interchangeable units beneath it) is explicitly out of scope for v1; if two identical products are owned, they are two Items.
- **Containment is scenario-scoped**: The "which item is packed inside which" plan is defined per scenario (packing for a situation), not as a permanent global storage graph. There is no per-item storage-location attribute in v1. If a permanent global containment model is desired instead, that is a future refinement.
- **Constraints & checklist deferred (iteration 14)**: All constraint functionality and the preparation checklist (prepared state, progress) are removed to reduce complexity; scenarios are pure item-assembly + packing trees for now. Either may return later under its own spec.
- **Acquisition-first & composition**: Items are created only within an acquisition and belong to exactly one; there is no standalone item-creation path and no acquisition-less item. Deleting an acquisition deletes its items (composition) behind a count-stating confirmation.
- **Currency handling**: the item's `sku_price` and each cost factor's `value` store a currency code string; the picker reads the finance domain's currencies over its API. Inventory does not import finance models or hold a DB foreign key to them (Principle II). No automatic FX conversion is performed within Inventory — `net_cost` is grouped by currency, so factors in different currencies are summed independently.
- **Units**: Dimension parameters draw units from fixed families (length: mm/cm/m/in; weight: g/kg/lb; volume: mL/L) normalized to a canonical base unit (mm, g, mL) for storage so cross-unit sort/filter is correct; the entered unit is retained for display. Units outside these families are represented with `numeric` or `string` parameters instead.
- **Platform consistency**: The Inventory app is delivered as a new domain within the existing unihub dashboard and reuses the established entity-centric backend structure, shared table component, service-layer pattern, navigation, i18n, and authentication — no new standalone application.
- **Deletion vs deprecation**: Deprecating (setting `deprecate_time`) marks an item retired but keeps it in the catalog (surfaced via the deprecated filter) and is reversible via Restore; hard deletion of an item happens through its acquisition (FR-009).
